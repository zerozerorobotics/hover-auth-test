# Session Sync V4 — Iframe 复用与 Cooldown 策略

## Iframe 复用 vs 销毁重建

### 方案对比

| 维度 | 复用 iframe (改 `src`) | 销毁重建 (当前实现) |
|------|----------------------|-------------------|
| DOM 操作 | 1 次 create，N 次改 `src` | 每次 create + remove |
| 内存 | iframe 常驻 DOM | 用完即销毁 |
| 可靠性 | 相同 `src` 可能被缓存 → 需 cache buster | 每次全新，无缓存问题 |
| 复杂度 | 略低 | 略高但更稳健 |

### 结论

**保持销毁重建**。原因：
- 有 cooldown 机制，不会频繁创建
- 销毁重建更可靠，避免 iframe 内部状态残留
- DOM 操作开销极小，不是性能瓶颈

---

## Cooldown 参数选择

当前值: **5 秒** (`iframeCooldownMs: 5 * 1000`)

### 5s Cooldown 的用户交互感知

```
用户操作时间线:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

0s    页面加载 → init() → checkSession() → 创建 iframe
~1-2s                                    postMessage → 状态同步完成 ✅

3s    用户切走 Tab
6s    用户切回 → visibilitychange
      checkSession() → cooldown 过期 ✅ → 创建 iframe → 检查 ✅

9s    用户又切走
11s   用户切回 → cooldown 过期 ✅ → 创建 iframe → 检查 ✅

12s   用户又切回 → cooldown 没过 ❌ → 跳过（静默，用户无感知）
```

### 用户体验总结

| 行为 | 体验 |
|------|------|
| 正常使用（切 Tab 间隔 > 5s） | **无感知**，每次切回静默检查 |
| 快速切 Tab（< 5s） | **无感知**，跳过检查，页面无表现 |
| 退出同步成功 | 页面跳转（~1-2s 后），**有感知** |
| 登录同步成功 | 页面跳转（~1-2s 后），**有感知** |

### 为什么不用 60s？

60s 对**退出同步**的影响：

```
0s:   切到 Site B → iframe 检查 → active ✅
5s:   切到 Site A → 退出
10s:  切回 Site B → 如果 60s cooldown → 跳过 ⚠️（最多等 60s 才同步）
```

但实际中这个场景极其罕见 — 用户从 "退出 Site A" 到 "切回 Site B" 通常远超 5 秒。

### 最终决策

保持 **5s**。理由：
1. iframe 创建销毁开销微乎其微
2. 5s 足够避免无意义的重复请求
3. 退出同步及时性有保障
4. 用户完全无感知
